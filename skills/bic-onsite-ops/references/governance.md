# 运维手册的编写与管理

依据 Drake 于 2026-09-21 明确的原则：内容规范、版本控制与定期评审、团队集中访问。
本文件定义管理规则；不表示已经部署知识库、配置定时任务或完成 Git 提交。

## 内容规范

每份操作手册按以下结构组织，短流程可合并相邻部分，但不省略操作边界和验证：

1. **目的与适用范围：** 解决什么问题，适用站点、服务、版本，以及不适用的情形。
2. **维护信息：** 维护责任人 / 团队、最后验证日期、验证版本或脚本指纹、评审状态。
3. **前置条件：** 访问路径、所需权限、凭据读取位置、服务状态和操作授权。
4. **诊断步骤：** 明确每个命令运行在 Mac、`.150` 还是 `.104`；写出预期结果和失败分支。
5. **处理步骤：** 编号列出操作、影响对象、保持不变的对象及停止条件；把只读命令与变更分开。
6. **验证与恢复：** 用实际结果验证恢复，列出未测试范围、备份位置和可用的回滚方式。
   不存在已验证回滚方式时明确说明，不编造逆操作。
7. **依据与关联记录：** 链接维护中的脚本、契约、故障记录和变更记录。

术语统一：`orin` 是站点 ID，也是现场有线 SSH alias；`orin-tel` 是 Tailscale SSH alias，
不称为 Telnet 协议。区分 Agent 的模拟 Mind、Robot Mock、Device provider 和真实控制服务。
区分 API key、monitor token、SSH 登录密码及 SSH 私钥；正文只记录用途与读取位置。

命令应可复制，但凭据用变量或私有存储读取，不提供真实值。使用适用日期约束网络地址、
端口、版本和已知缺陷，不把一次现场快照当永久事实。明确“配置有效”“服务健康”与
“完整业务流程通过”的证据差异。

## 版本控制与变更管理

- `c12-ai/noosphere-arsenal/skills/bic-onsite-ops/` 是本 Skill、随包手册和脱敏故障记录的唯一维护源；全局安装副本通过 `npx skills` 更新，不单独维护。BIC 部署工具仍由 BIC-meta 维护。故障经过与可重复步骤分开保存。
- 每次故障处理后更新案例。只有实际改变了通用步骤或边界时才修改手册，避免复制案例全文。
- 操作步骤、目标选择、授权边界或回滚方式改变时，变更说明必须写明原因、影响与验证证据，
  按仓库正常评审流程提交。现场紧急修订应明确“未评审”，后续补评审，不宣称已合并。
- 用 Git commit / PR 追踪文档修订，不为每次文字调整人为创建发布标签或重复维护整份 changelog。
- 旧流程保留可追溯历史；现行页面标明已替代、适用旧版本和新入口，避免两套冲突步骤并存。
- 凭据文件留在批准的私有存储中。版本控制和知识库只管理凭据字段、用途及读取方式。

## 定期与事件触发评审

故障恢复后、服务或脚本升级后、网络入口变化后、凭据机制变化后，都应复核受影响页面。
除此以外，维护团队应约定固定评审周期，并登记负责人、最近评审日期、下次到期日期及结论。
具体负责人和周期尚未由团队指定；在指定前标记“待确定”，不得伪造已安排的评审或自动提醒。

评审至少检查：

- 链接和脚本入口是否有效，命令是否与当前版本一致。
- 只读检查是否真的只读，影响范围与授权要求是否仍准确。
- 已知缺陷是否已修复，是否需要撤销历史绕行步骤。
- 验证证据是否覆盖文档承诺；失效或未经复核的步骤标记“待复核”，不作为自动恢复依据。
- 是否泄露凭据、产生重复维护源或遗漏故障记录。

文档评审不等于获得现场重启、重连、重置或实验下发授权；无法无副作用复核时，记录需要
验证的项目，不为了评审而重演真实操作。

## 团队知识库

知识库可以提供统一目录、搜索、访问权限和团队阅读入口。当前建议保留 Git 为步骤的维护源，
知识库采用链接或受控单向发布，并展示源路径、commit、发布时间及维护人。
若以后决定以知识库为编辑源，先明确同步方向和冲突处理，不同时维护两份独立正文。
只有实际完成发布及访问验证后，才能声称团队已同步；部署知识库需要另行明确范围。
